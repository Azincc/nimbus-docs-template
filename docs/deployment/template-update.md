应用模板后，你的部署仓库保存了一份模板代码。官方模板有更新时，需要将代码同步到这个仓库，再由 Cloudflare 构建和发布。

本文介绍更新原站点的方法。继续使用原来的部署仓库和 Worker，可以保留已有域名及 Cloudflare 中的构建变量和机密。

## 1. 找到需要更新的仓库

打开 Cloudflare 的 **Workers 和 Pages → 你的 Worker → 设置 → 构建**，查看 **Git 存储库** 和 **生产分支**。这里关联的仓库才是需要更新模板代码的部署仓库。

`DOCS_REPO` 指定的是文档源仓库，负责保存 Markdown、图片和站点配置。它可以与部署仓库相同，也可以是另一个仓库。只更新文档源，或在 Cloudflare 重试构建，都不会自动同步官方模板代码。

打开部署仓库的 GitHub 页面，按以下情况选择操作：

| 仓库情况 | 更新方法 |
| --- | --- |
| 仓库名称下方显示 `forked from Azincc/nimbus-docs-template`，并有 **Sync fork** 按钮 | 使用下面的 GitHub 网页同步步骤 |
| 通过 **Deploy to Cloudflare** 创建的独立副本，没有上述 Fork 关系 | 将下面的更新提示词交给能操作仓库的 Agent 或维护者 |

当前模板没有内置“同步模板”工作流。独立副本的用户可以按第 4 节交给 Agent 协助，不需要自己输入 Git 命令或重新创建 Worker。

官方模板：[Azincc/nimbus-docs-template](https://github.com/Azincc/nimbus-docs-template)。可在[提交记录](https://github.com/Azincc/nimbus-docs-template/commits/main/)查看近期变化。

## 2. 更新前确认自己的内容和配置

更新时需要保留：

- 自己的文档、图片、站点 JSON，以及修改过的页面或样式。
- 部署仓库 `wrangler.jsonc` 中的 Worker 名称、公开参数默认值和自己的部署设置。
- Cloudflare **构建 → 变量和机密** 中已配置的参数。同步仓库不需要删除或重新填写这些值，也不需要导出机密。

例如，部署仓库中的 Worker 名称应保持自己的名称，不能改回官方示例的 `nimbus-template`。自己的文档仓库地址也应继续保留。参数说明见[修改部署配置](./configuration.md)。

## 3. Fork 仓库：在 GitHub 页面同步

1. 打开自己的部署仓库，切换到 Cloudflare 使用的生产分支，通常为 `main`。
2. 点击 **Sync fork → Update branch**，同步官方仓库的更新。
3. 如果 GitHub 提示有冲突，交给 Agent 或维护者按下一节处理，并核对上面列出的用户内容和配置。
4. 同步成功后，到 Cloudflare 查看新提交对应的构建和部署记录。

这个入口仅适用于真正 Fork 自官方模板的仓库。如果仓库没有 Fork 关系，使用下一节的方法。

## 4. 独立副本：交给 Agent 更新

准备好部署仓库地址、生产分支和 Worker 名称，将下面的提示词交给能够使用 Git 并访问部署仓库的 Agent。也可以请维护者按提示词中的步骤操作。

本页使用 Nimbus 的 Agent 阅读功能：点击页面顶部的 **Copy page** 可以复制包含提示词的整页 Markdown；**View as Markdown** 可以打开适合 Agent 读取的版本。也可以直接复制下面的提示词，填写站点信息。

你可以这样发起任务：“请按这份文档中的 Agent 提示词，帮我准备模板更新。”如果希望 Agent 继续推送、合并并发布，也请在任务中明确说明范围。

### 给 Agent 的更新提示词

```text
你正在协助更新一个已经部署到 Cloudflare 的 Nimbus 文档站。
请将官方模板的更新合入现有部署仓库，并保留用户文档、配置、定制和原 Worker。

站点信息（由用户填写；已能从当前环境确认的项目不必重复询问）：
- 部署仓库：填写 Cloudflare“设置 → 构建”中关联的 GitHub 仓库地址。
- 生产分支：填写实际分支，通常为 main。
- Worker 名称：填写现有 Worker 名称。
- 网站地址：填写原站点地址，用于更新后验证。

官方模板：https://github.com/Azincc/nimbus-docs-template.git
上游分支：main

执行范围：
以用户本次任务的实际授权为准，本提示词本身不授予推送、合并或部署权限。
先完成仓库核对、更新分支、冲突处理和核心验证；在用户已授权的范围内继续推进。
若尚未授权发布，交付可审阅的本地更新结果，并说明剩余步骤。

请按以下顺序执行：

1. 确认目标仓库
   阅读仓库的 AGENTS.md、AGENT.md 和相关项目约定。
   核对 git remote -v、当前分支及 git status。
   确认操作的是 Cloudflare 关联的部署仓库，而不是仅保存 Markdown 的 DOCS_REPO。
   仓库或生产分支无法确定时，先询问这一必要信息，不猜测。
   用户有未提交工作时使用独立工作目录保留其工作，不重置或覆盖。

2. 准备更新分支
   获取生产分支的最新提交，记录更新前 SHA，再从它创建独立更新分支。
   为官方模板配置并核对 upstream；名称已被其他仓库占用时使用新的远程名称。
   获取官方 main，记录完整目标 SHA。本次合并固定使用该提交。
   已包含该目标且无须更新时，直接报告结果，不创建空更新。

3. 合并官方更新
   在更新分支执行 Git 合并，检查后再提交：
   git merge --no-ff --no-commit --allow-unrelated-histories <已确认的上游完整 SHA>
   将尖括号部分替换为真实 SHA，不能原样运行占位符。
   --allow-unrelated-histories 用于兼容 Cloudflare 创建的独立仓库历史。
   检查自动合并和冲突文件，不对整个仓库统一使用 ours、theirs 或强制覆盖。

4. 保留用户内容和配置
   保留用户文档、图片、站点 JSON、定制页面和样式，避免混入官方示例内容。
   wrangler.jsonc 保留原 Worker 名称、vars、账户、域名和其他用户部署设置；
   按字段补入新版必要配置，不将自己的名称改回 nimbus-template。
   package.json 保留用户包名及必要定制，并确保依赖与 pnpm-lock.yaml 一致。
   同步相互依赖的构建脚本、布局、组件和样式，逐项处理双方修改。
   Cloudflare 已有构建变量和机密继续保留，不导出或复制机密到仓库。
   DOCS_TOKEN 仅用于 Git fetch，不能写入配置、日志、提示词或静态产物。
   源文档只写入临时或生成目录，不在 src/content/docs/ 维护文档。

5. 完成核心验证
   检查无未解决冲突，核对差异，并运行 git diff --cached --check。
   本地已具备对应文档源配置时，按项目要求执行：
   pnpm install --frozen-lockfile
   pnpm run build
   本地配置可能不同于 Cloudflare；明确本次验证实际使用的文档源。
   私有文档可使用 Cloudflare 已配置的分支构建验证，不要求用户把 Token 发到聊天。
   只做必要检查。缺少权限或构建条件时，说明尚未验证的项目，不报告成功。
   无法可靠解决冲突时，列出文件和需要用户决定的内容，保留现场供审阅。

6. 在授权范围内提交和发布
   仅提交已核对的变更；推送更新分支后，向实际生产分支创建 Pull Request。
   说明新增功能、用户配置保留情况和验证结果。
   合并时使用 Create a merge commit，保留上游历史，便于下次同步；
   若仓库限制该方式，先说明限制，不悄悄改用 Squash 或 Rebase。
   不强制推送，不新建 Worker，不改变原站点域名。

7. 确认完成状态
   获准发布后，确认包含本次更新的新提交在 Cloudflare 构建、部署成功，
   检查原站点首页、搜索和本次更新的功能。
   重试旧构建不能代替构建新模板代码。
   页脚及 /_build.json 的 SHA 是文档版本，不能单独证明模板已更新。

最后请报告：
- 部署仓库、生产分支、更新前 SHA、官方目标 SHA。
- 本次变化与用户配置保留情况。
- 已完成的检查、未验证项及冲突。
- 实际达到的状态：本地准备、已推送、已创建 PR、已合并或已部署。
- 有实际 PR 或成功部署时提供对应链接；需要用户操作时给出具体下一步。
```

上述提示词同时保留在本页 Markdown 中，部署后路径为 `/deployment/template-update/index.md`，并可由 Nimbus 的 `llms.txt` 索引发现。提示词也会在普通页面显示，方便用户检查后交给 Agent。

## 5. 确认网站更新成功

1. 在 Cloudflare 找到合并后新提交对应的构建记录，确认构建与部署均成功。
2. 打开原来的站点地址，检查首页、侧栏、搜索及本次需要的新功能。
3. 查看 **设置 → 构建 → 变量和机密**，确认参数仍为自己的值。

新增模板代码必须构建包含它的新提交。重试一个旧提交的构建，不会读取之后才合并的代码。如果没有自动触发，检查 Cloudflare 关联的仓库、生产分支和自动构建设置，或使用已配置的[构建挂钩](./deploy-hook.md)触发当前分支构建。

当前页脚和 `/_build.json` 展示的是文档源提交。只更新模板脚本时，这个值可能不变；应结合 Cloudflare 的部署仓库提交及实际页面功能确认更新结果。

如果更新请求还未合并，可以关闭它。合并后需要回退时，请维护者撤销对应更新请求的合并提交并重新部署；紧急情况下可先在 Cloudflare 恢复先前成功的部署，再同步处理仓库代码。
